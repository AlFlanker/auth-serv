# Функции identity-service

Сервис выдаёт пользовательские JWT, предоставляет профиль и роли из выбранного источника, ведёт реестр токенов в PostgreSQL. Внешний SSO удостоверяет личность сотрудника. Приложение, которое принимает JWT, проверяет его и решает, разрешена ли пользователю конкретная операция.

## Вход и выдача JWT

**Вход через SSO.** Доверенный шлюз удаляет переданный клиентом SSO-заголовок и после аутентификации подставляет канонический логин. Имя заголовка берётся из `OSSConfig.headerName`. Шлюз вызывает `POST /api/v1/token` без тела. Сервис отбрасывает конечный суффикс `^M`, перечитывает профиль и права из ОШС или ЮСБ в обход кэша и сверяет логин с учётом регистра. Неизвестный логин или неоднозначный заголовок дают `401`. Прямой доступ к этому маршруту следует ограничить доверенным шлюзом.

**Дополнительные способы входа.** По умолчанию сервис читает идентификатор из заголовка. При `identity.auth.sso-cookie-enabled=true` он также принимает одноимённую cookie, если заголовок отсутствует или пуст. Шлюз должен проверять и перезаписывать такую cookie. При `identity.auth.local-password-enabled=true` и отсутствии SSO-идентификатора тот же маршрут принимает JSON `{"username":"<login>","password":"<password>"}`. Локальная учётная запись должна быть включена и иметь BCrypt-хеш пароля. Неверные данные дают `401`, отсутствие обязательного поля в режиме парольного входа — `400`.

**Ответ с токеном.** После регистрации идентификатора токена `jti` сервис возвращает `200` и заголовок `Cache-Control: no-store`. Поле `expiresInSeconds` показывает фактический срок действия в секундах. При стандартном TTL 30 минут ответ выглядит так.

```json
{"accessToken":"<signed-jwt>","tokenType":"Bearer","expiresInSeconds":1800}
```

**Проверка подписи и прав.** `GET /.well-known/jwks.json` возвращает `200` и объект `{"keys":[…]}` с публичными RSA-ключами. Получатель загружает ключи с настроенного HTTPS-адреса, выбирает ключ по `kid`, проверяет `alg=RS256`, `typ=at+jwt`, подпись, ожидаемый `iss`, свой идентификатор в `aud` и срок действия. Логин содержится в `sub` и `username`, роли — в `roles`, источник входа — в `auth_source`. Для активной организации сервис включает `org_guid` и `org_code` по отдельности, если соответствующее значение есть в профиле.

## Профиль, организации и роли

**Доступ внутреннего клиента.** Каждый запрос под `/api/internal/**` требует одного заголовка `X-Internal-Key` со значением `identity.internal.api-key`. Все доверенные клиенты используют общий секрет. Право конечного пользователя читать или менять данные указанного логина проверяет вызывающее приложение. При отсутствующем, повторном или неверном ключе сервис возвращает `401`. Ключ хранится на сервере вызывающей системы.

**Профиль и организации.** `POST /api/internal/v1/users/profile` с телом `{"login":"<login>","bypassCache":false}` возвращает `200` и JSON с полями `login`, `fullName`, контактами, `roles`, `organizations` и `cacheHit`. `cacheHit=true` означает, что профиль отдан из кэша сервиса, `false` — загружен из источника (ОШС/ЮСБ). При `bypassCache=true` сервис обходит кэш и всегда отвечает `cacheHit=false`. Сервис выбирает активную организацию, когда в собранном профиле ровно одна запись. Поля `activeOrgCode` и `activeOrgGuid` заполняются при наличии данных. Адаптер ЮСБ сейчас использует только первую запись из `employees`, поэтому профиль ЮСБ может содержать неполный список организаций. Для списка организаций используйте `POST /api/internal/v1/users/organizations` с телом `{"login":"<login>"}`. Оба метода возвращают `404`, если профиль не найден.

**Группы пользователя.** `POST /api/internal/v1/users/groups` с телом `{"login":"<login>"}` запрашивает права напрямую из настроенного источника и возвращает `200` с массивом строк. При отключённой загрузке групп результат равен `[]`. Если загрузка включена и источник вернул пустой список, результат равен `["ROLE_UNDEFINED"]`.

**Обновление атрибутов.** `POST /api/internal/v1/users/custom-attributes` принимает JSON `{"login":"<login>","attributes":{…}}` с парами «имя атрибута — строковое значение». При получении объекта `SimpleResponse` от СОБИ сервис сбрасывает локальную запись кэша пользователя и возвращает `204` без тела. Значение поля `result` сервис сейчас не проверяет. Для ЮСБ операция возвращает `501`, при таймауте команды — `504`, при недоступности источника или отсутствии подтверждения — `503`.

**Инвалидация кэша.** `POST /api/internal/v1/users/cache/invalidate` без тела полностью сбрасывает кэш профилей и возвращает `204`. Используется монолитом fk-portal при инвалидации кэша профилей во внешнем режиме.

**Справочник локальных ролей.** `GET /roles` возвращает `200` с массивом объектов `{"id":"…","name":"…"}` из PostgreSQL. `GET /roles/{id}` возвращает одну роль или `404`. Эти маршруты доступны без `X-Internal-Key`. Для получения ролей, назначенных конкретному пользователю в ОШС или ЮСБ, используется метод `groups`.

## Обмен и выход

**Обмен.** `POST /api/internal/token/exchange` принимает `Authorization: Bearer <jwt>` и `X-Internal-Key`, тело пустое. Сервис проверяет JWT и его запись в реестре, перечитывает права пользователя из источника входа, затем одной транзакцией погашает старый `jti` и регистрирует новый. Ответ `200` имеет тот же формат, что первичная выдача. Обмен сохраняет исходный `auth_time`. По умолчанию цепочка обменов ограничена восемью часами от первичной выдачи. Истёкший, уже обменённый или отозванный токен даёт `401`. Если ответ успешного обмена потерян, клиенту нужна первичная выдача.

**Выход.** `POST /api/v1/logout` с `Authorization: Bearer <jwt>` отзывает предъявленный `jti` и возвращает `204` без тела. Повторный выход с тем же JWT, пока он проходит проверку, также даёт `204`. Отсутствующий или невалидный JWT даёт `401`. Отзыв блокирует дальнейший обмен этого токена. Потребитель, проверяющий только подпись и claims, может принимать его до истечения срока с учётом допуска часов. Завершением внешней SSO-сессии управляет провайдер.

## Пример бизнес-процесса

Сотрудник открывает в портале карточку организации. По правилам этого примера карточку видит сотрудник с правом просмотра и с подтверждённой принадлежностью к этой организации. Портал принимает решение о доступе, а identity-service предоставляет проверенный логин, роли и сведения об организации. Это пример для будущей интеграции портала.

1. Шлюз аутентифицирует сотрудника через SSO и отправляет его логин в `POST /api/v1/token`. Получив `accessToken`, сервер приложения проверяет подпись по JWKS, срок действия, аудиторию и наличие роли, необходимой для просмотра карточки.
2. Для показа ФИО и организации сервер берёт логин из проверенного `sub` и запрашивает профиль с внутренним ключом. Портал сверяет идентификатор запрошенной организации с данными профиля. При подтверждённом совпадении показывает карточку и `fullName` сотрудника.

   ```http
   POST /api/internal/v1/users/profile HTTP/1.1
   Host: <identity-service-host>
   X-Internal-Key: <internal-service-key>
   Content-Type: application/json

   {"login":"<login>","bypassCache":false}
   ```

3. Перед истечением JWT сервер вызывает `POST /api/internal/token/exchange` и заменяет сохранённый токен полученным. Если права сотрудника изменились, сервер применяет роли из нового проверенного JWT при следующем решении о доступе.
4. При выходе сервер предъявляет текущий JWT в `POST /api/v1/logout` и удаляет его из сессии приложения. При следующем открытии приложения шлюз снова устанавливает личность сотрудника по правилам SSO.

## Доступность сервиса

`GET /actuator/health/liveness` показывает состояние процесса, `GET /actuator/health/readiness` учитывает состояние приложения, БД и конфигурацию SSO. Готовность означает, что необходимые настройки источника присутствуют. Доступность ОШС или ЮСБ для конкретного пользователя проверяется при вызове самого API. Метрики для Prometheus доступны по `GET /actuator/prometheus`.

См. [настройки приложения](configuration.md) и [порядок ротации ключей](../README.md#ключи-и-ротация).
