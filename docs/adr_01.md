Проблематика:
Архитектурные недостатки монолита
Текущая монолитная архитектура ЕТД порождает системные риски и ограничения:

Отсутствие отказоустойчивости: Критическая ошибка в любом модуле (напр., утечка памяти в Jetty-сессиях) приводит к остановке всего приложения, а не только проблемного функционала. Из-за sticky session деградация в модуле навигации сказывается сразу на большую группку пользователей. Это напрямую влияет на доступность сервиса/API.

Невозможность гибкого масштабирования: Невозможно масштабировать ресурсоемкие части системы независимо от остальных. Весь монолит потребляет до 48 Гб Heap, что ведет к неэффективному использованию вычислительных ресурсов.

Несоответствие облачной инфраструктуре (k8s)(цель к 2027): Монолит не соответствует философии Kubernetes, ориентированной на слабосвязанные, легко оркестрируемые микросервисы/сервисы. Это затрудняет автоматическое масштабирование, развертывание и отказоустойчивость на целевой инфраструктуре.

Технический долг и блокирующие обновления: Обновление стека технологий (Spring Boot 3, JDK 25+) сопряжено с чрезмерными затратами (30+ человеко-дней на незавершенный переход) и высокими рисками из-за сильной связанности кода. Это блокирует получение преимуществ новых версий (производительность, безопасность).

Проблемы в ключевом функционале

Самописный механизм проксирования запросов: Реализация содержит сложную, запутанную логику, основанную на допущениях, что является источником периодических ошибок. Высокие затраты на поддержку и развитие этого механизма.

Неэффективный механизм получения деревьев навигации: Использование Reactor нивелируется наличием блокирующих операций в цепочке. Невозможно быстро масштабировать.

Так же с 2026 года ожидается кратный рост нагрузки, и текущая модель “масштабируем весь монолит” становится экономически/технически неэффективной!!

Варианты решения:
Вариант 1
Оставляем текущую монолитную архитектуру как единый deployment unit. В рамках миграции на Spring Boot 3+ выполняем точечный рефакторинг “критичных” участков: проксирование (переход на Netty/WebClient), отказоустойчивость (Hystrix → Resilience4j), кэширование/оптимизация навигации (параллелизация SOAP-вызовов, улучшение локального/распределённого кэша). Внешние API не меняются.

Плюсы:

Минимальные организационные изменения: один артефакт, знакомые процессы деплоя/эксплуатации.

Минимальный риск по обратной совместимости (нет изменения внешней топологии).

Минусы:

Остаётся высокая связность: сбой/деградация одного функционала (навигация/прокси/уведомления) влияет на весь runtime.

Ограниченный потолок оптимизаций: даже при переходе на Netty часть узких мест остаётся системной (единый heap, общие пулы, общий GC, общие релизы).

Риск дальнейшего роста инфраструктурной стоимости: горизонтальное масштабирование = увеличение числа тяжёлых инстансов и памяти, вместо точечного скейлинга.

Не решает целевую задачу изоляции деградаций и точечного масштабирования навигации/прокси под ожидаемый рост в 2026+.
Вариант 2
Переходим от монолита к сервис-ориентированной архитектуре с сохранением единой точки входа и обратной совместимости. Внешний API для клиентов остаётся прежним. Внутренне функциональность поэтапно выносится в отдельные сервисы, прежде всего:

API Gateway (Edge/BFF),

Navigation Service (построение дерева + проверки доступности),

Config Service,

Auth Service (выдача JWT и сбор пользовательского профиля из ОШС/ЮСБ),

Comms Service (уведомления + обращения в техподдержку в одном deployment unit на первом этапе).

Плюсы
Независимое масштабирование критичных частей: NavigationService и API Gateway можно масштабировать отдельно от остального, снижая стоимость роста нагрузки.

Снижение потребления ресурсов: вместо 16 тяжёлых JVM (48 ГБ heap) - несколько специализированных сервисов меньшего размера с целевыми параметрами памяти/пулов.

Повышение отказоустойчивости: деградация навигации/внешних источников не обязана ронять весь runtime.

Плавная миграция без изменения клиентов: единая точка входа сохраняется; изменения происходят за API Gateway.

Технологическое обновление ускоряется: новые сервисы можно сразу делать на Spring Boot 3 / WebFlux / Resilience4j, без переписывания всего монолита разом.

Лучшее разделение ответственности и сопровождение: отдельные доменные контуры (Auth, Nav, Config, Comms) проще развивать и наблюдать (метрики/трейсы).

Минусы / Риски
Больше deployment units, больше сетевых взаимодействий, необходимость service discovery/конфигурации. На ранних порах будет решать настройками Edge(API GateWay).
Требуется зрелость эксплуатации: мониторинг, алерты, трассировка, централизованные логи, политики обновления конфигов (etcd watch), контроль версий API.

На схеме минимальный набор сервисов в рамках переход на SOA.

До перехода в k8s, при необходимости масштабироваться, необходимо ставить балансеры между сервисами, например Edge Service ↔NGINX ↔Navigation Service.

Решение:
Вариант 2 (SOA) как целевую архитектуру.
Причины:

ожидаемый кратный рост нагрузки с 2026 года,

необходимость точечного масштабирования навигации и прокси,

снижение стоимости инфраструктуры,

возможность поэтапной миграции без изменения клиентов (единая точка входа через API Gateway).



Принятое решение
Вариант 2 13.01.2026 

1. Основные компоненты (Сервисы)
   В центре архитектуры находится Edge/API Gateway Service (шлюз), который является единой точкой входа для трафика.

Edge/API Gateway Service: Центральный узел, маршрутизирующий запросы, собирающий данные о профиле и конфигурациях.

Navigation Service: Сервис, отвечающий за навигацию.

Auth Service: Сервис аутентификации и авторизации.

Config Service: Сервис управления конфигурациями.

Common Service: Общий сервис (взаимодействует со своей БД).

2. Хранилища данных и кэши
   Configuration ETCD: Распределенное хранилище ключ-значение для конфигураций.

User cache Redis/gRPC: Кэш пользовательских данных.

Configuration DB: База данных для общего сервиса.

Prometheus/Grafana + ELK: Системы мониторинга (метрики) и логирования.

3. Внешние системы и интеграции
   Балансировщик нагрузки (сверху): Принимает внешний трафик и направляет его в Edge/API Gateway.

Безопасность: Блок внешних систем, включающий ОШС и USB (вероятно, аппаратные ключи или специфические системы безопасности).

Целевые бэкенды: Конечные сервисы (на схеме их несколько), куда Gateway перенаправляет трафик после авторизации.

4. Потоки данных и взаимосвязи (Кто с кем и как общается)
   Внешний контур:

Балансировщик нагрузки -> Edge/API Gateway: Входящий трафик.

Работа с навигацией:

Edge/API Gateway -> Navigation Service: Отправляет «Запрос навигации».

Navigation Service -> Edge/API Gateway: Возвращает «получение навигации».

Navigation Service -> Configuration ETCD: Выполняет «Чтение конфигов».

Работа с профилем и авторизацией:

Edge/API Gateway -> Auth Service: Запрашивает «Детали профиля и кеш навигации».

Auth Service -> Edge/API Gateway: Возвращает «Детали профиля».

Auth Service <-> Безопасность (ОШС, USB): Двустороннее взаимодействие для проверки.

Auth Service <-> User cache Redis/gRPC: Двусторонний обмен данными (чтение/запись кэша).

Работа с конфигурациями:

Edge/API Gateway -> Config Service: Отправляет запрос на «Чтение конфигов».

Config Service <-> Configuration ETCD: Двустороннее взаимодействие («чтение и запись конфигурации»).

Маршрутизация бизнес-запросов:

Edge/API Gateway -> Целевые бэкенды: Перенаправление запросов в целевые сервисы после успешной проверки.

Общий сервис:

Common Service <-> Configuration DB: Двусторонний обмен данными с базой.

5. Мониторинг и Логирование (Observability)
   На схеме практически все сервисы отправляют стрелки «Метрики/логи».

Navigation Service, Edge/API Gateway, Auth Service, Config Service и Common Service отправляют метрики/логи в сторону верхнего уровня (агрегация к Балансировщику/шлюзу) и вниз — в систему Prometheus/Grafana + ELK
